## Hallazgos prioritarios

### P1 — La configuración local permite omitir HMAC

Referencia: `src/app.js:58-74`. Si se inicia con el `.env` inspeccionado y sin variables externas adicionales, la ausencia de `NODE_ENV` se interpreta como development y, al faltar `APP_SECRET`, se aceptan POST sin firma. Esto bloquea la exposición pública mediante túnel o despliegue. Configurar el secreto de la aplicación y el entorno explícito; verificar que solicitudes sin firma y con firma incorrecta se rechacen. No se modificó `.env`.

### P1 — Una respuesta de catálogo puede anular la pausa humana

Referencias: `src/app.js` lee el estado una vez antes de despachar; `src/services/state.service.js:497,520,625` persiste estados sin serialización por cliente.

Reproducción: ejecutar simultáneamente `processMenuOption(phone, '1')` y `processMenuOption(phone, '6')` sobre el servicio real aislado produce las transiciones **PAUSED_HUMAN → CATALOG**. Una secuencia larga ya iniciada termina después del handoff y vuelve a habilitar al bot. La deduplicación por wamid no ordena dos mensajes distintos. Serializar trabajo por teléfono y proteger transiciones frente al handoff; probar también las rutas cortas y reanudación explícita.

### P1 — Solo se procesa el primer mensaje de un webhook

Referencia: `src/app.js:209-215`. El código usa `[0]` para entry, changes y messages. Reproducción: un payload con dos mensajes recibe HTTP 200, pero solo se reserva/procesa el primero. Iterar todos los mensajes de todas las entradas/cambios, con aislamiento de errores y deduplicación individual.

### P1 — Confirmación prematura y reserva definitiva pueden perder trabajo

Referencias: `src/app.js:203,228`; `src/services/dedup.service.js`. Se devuelve HTTP 200 antes de la reserva y la persistencia. Un error de BD posterior se registra sin cambiar esa respuesta. Si el fallo sucede después de reservar el wamid, un reintento se descarta aunque el procesamiento no haya concluido.

Es una limitación ya reconocida en BRIEF-002, no una regresión nueva. La suite incluso caracteriza el HTTP 200 cuando falla la reserva. Para aumentar la fiabilidad, persistir duraderamente la recepción antes de confirmarla y modelar procesamiento/recuperación con idempotencia de los efectos de salida. No basta con borrar reservas y reenviar todo: podría duplicar respuestas ya aceptadas.

### P1 — Un error leyendo estado puede hacer responder a un cliente pausado

Referencia: `src/services/state.service.js:320-330`. `getUserState` convierte cualquier fallo de consulta en ORGANIC. Reproducción con fallo simulado: devuelve ORGANIC. Si falla esa lectura y las operaciones posteriores funcionan, un cliente previamente en PAUSED_HUMAN puede recibir saludo y menú, y terminar en MENU. Distinguir cliente inexistente de error de persistencia y detener/reintentar este último conservando la pausa.

### P2 — El catálogo invita a una interacción que la V1 no resuelve

Referencia: `src/services/state.service.js:490,513`. Las rutas 1 y 2 piden escribir nombre o número del modelo para consultar tallas/precios. El webhook solo enruta opciones generales: un nombre libre lleva al menú y un número puede disparar otra ruta. Las rutas 3/4 ya fueron corregidas con derivación explícita. Aplicar el mismo criterio a 1/2, orientando hacia la opción 6 mientras no exista selección de producto.

### P2 — Comparación Unicode provoca excepción en el login

Referencia: `src/routes/dashboard.js:55-58`. Se comparan longitudes de strings antes de `timingSafeEqual`, que exige igualdad de bytes. Reproducción con contraseña esperada sintética de siete caracteres ASCII y entrada de siete caracteres `é`: **ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH**. La excepción ocurre antes de incrementar el contador de intentos. Comparar longitudes de buffers y devolver rechazo controlado; aplicar también al token de sesión que usa el mismo helper.

### P2 — El bloqueo de login no reinicia al expirar

Referencia: `src/routes/dashboard.js:165-185`. Al expirar `bloqueadoHasta`, ese valor y el contador no se limpian. Reproducción: cinco fallos, avance de 600001 ms, otro fallo y después contraseña correcta → **401, 429**. El primer error posterior al vencimiento renueva inmediatamente el bloqueo de diez minutos. Restablecer la ventana al expirar el bloqueo; la prueba actual solo verifica el primer 401 y no detecta el rebloqueo.
